# ADR-0001 — Arquitetura inicial do Ryoku OS

- **Status:** Proposto / Aceito para fundação (Missão 001)
- **Data:** 2026-11-06
- **Decisores:** Missão 001 (fundação Ryoku OS)

## Contexto

Ryoku OS precisa nascer com uma arquitetura clara que preserve:

1. **OS + UX** como produto (não apenas um conjunto de pacotes).
2. **Zaquion Core** como componentes Rust próprios (ferramentas e serviços).
3. **Kernel Linux upstream** sem modificações iniciais, mas preparado para integrações Rust futuras.
4. **Ryoku Desktop** como GUI existente a portar depois (projeto irmão).
5. **Compatibilidade** com Nix, Debian e Arch via integração/isolamento.
6. **Testes** progressivos em QEMU/KVM e **distribuição** futura (ISO + perfis).

Riscos a evitar na fundação: fork precoce do kernel, monólito de licenças incompatíveis, inventar clones de projetos irmãos, e prometer ISO/boot sem harness.

## Decisão

Adotar uma arquitetura em **camadas com repositórios/pastas separados por obrigação e ciclo de vida**:

```
┌─────────────────────────────────────────────────────────┐
│  Ryoku Desktop (externo, port futuro)                   │
│  Apps de usuários (apps/)                               │
├─────────────────────────────────────────────────────────┤
│  Zaquion Core (Rust) — serviços, tools, daemons         │
├─────────────────────────────────────────────────────────┤
│  Userland de base — proveniente de perfil/compat        │
│  (Debian e/ou Nix e/ou Arch via integração/isolamento)  │
├─────────────────────────────────────────────────────────┤
│  Linux kernel upstream (não modificado inicialmente)    │
│  [futuro: módulos/integrações Rust sob processo]        │
├─────────────────────────────────────────────────────────┤
│  Hardware / QEMU virtio (teste) / bare metal (depois)   │
└─────────────────────────────────────────────────────────┘
```

### Separações obrigatórias

| Fronteira | Motivo |
|-----------|--------|
| **Kernel ↔ resto** | GPLv2 do Linux; ciclo de rebase LTS; evitar misturar código first-party no tree sem processo |
| **Zaquion Core ↔ Desktop** | Ciclos de release diferentes; Desktop já existe fora; evita acoplamento prematuro |
| **Compatibilidade Nix/Debian/Arch** | Modelos de pacote distintos; preferir *adapters* a um único rootfs híbrido na fundação |
| **Packaging/ISO ↔ desenvolvimento** | ISO é artefato; fonte e harness vivem no monorepo |

### Escolhas concretas (Missão 001)

1. **Monorepo `ryoku-os` na raiz do Git atual** — ver [layout.md](layout.md).
2. **Não vendorar** a fonte completa do Linux nesta fase; `kernel/` é documentação + futuros pins/scripts.
3. **Zaquion Core** em Rust (toolchain já presente no ambiente de fundação: rustc/cargo 1.83).
4. **Licenças por componente**, não “um SPDX para tudo” — ver [../licensing/strategy.md](../licensing/strategy.md).
5. **Testes QEMU documentados primeiro**, execução e ISO em missões posteriores — ver [../testing/qemu-strategy.md](../testing/qemu-strategy.md).
6. **Perfis** Lite / Full / Gaming / Server como *metadados de packaging*, não como forks do repositório.

## Alternativas consideradas

### A. Distro clássica “fork do Debian/Arch com patches no kernel”

- **Prós:** caminho conhecido de ISO.
- **Contras:** custo de manutenção do kernel; identidade Zaquion diluída; UX/Desktop acoplados cedo.
- **Rejeitada** para o início.

### B. Apenas flake NixOS renomeado

- **Prós:** reprodutibilidade forte.
- **Contras:** aliena usuários Debian/Arch; não expressa Zaquion Core como produto; Desktop e ISO ainda precisam de processo próprio.
- **Rejeitada** como *única* base; Nix permanece canal de compatibilidade.

### C. Microkernel / kernel próprio

- **Prós:** controle total.
- **Contras:** anos de drivers/hardware; fora da visão “Linux upstream”.
- **Rejeitada**.

### D. Monorepo incluindo cópia inventada do Desktop e do NixOS

- **Prós:** “tudo num lugar”.
- **Contras:** viola a missão (não inventar cópias); risco de licença/histórico falso.
- **Rejeitada**.

## Consequências

### Positivas

- Fronteiras de licença e de release claras.
- Espaço para Rust first-party sem tocar no kernel.
- Caminho explícito para QEMU → instalador → perfis.
- Projetos irmãos preservados para integração futura.

### Negativas / custos

- Mais documentação e disciplina de ADR no início.
- ISO e “bootável” ficam adiados até o harness existir.
- Compatibilidade multi-ecossistema exige adapters (trabalho contínuo).

### Neutras

- Escolha futura de imagem base (Debian cloud vs Arch bootstrap vs Nix) fica em ADR posterior.
- rust-for-linux / out-of-tree modules ficam na Fase 6 do [ROADMAP.md](../../ROADMAP.md).

## Compliance com a visão

| Requisito da visão | Como esta ADR atende |
|--------------------|----------------------|
| OS + UX | Camadas de sistema + Desktop externo com port planejado |
| Zaquion Core Rust | Pasta e mandato first-party |
| Kernel upstream | Sem patches na fundação; pasta `kernel/` só referência |
| Compat Nix/Debian/Arch | `compatibility/` + docs |
| Testes QEMU/KVM | Estratégia documentada; execução em missão futura |
| ISO + perfis | `packaging/profiles/`; pipeline em fases 4+ |
| Docs PT/EN | README + política em CONTRIBUTING |
| GitHub público | Templates `.github/`; remoto público pós-revisão |
